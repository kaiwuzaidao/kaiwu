# Kaiwu AI 协作开发指南

产品可以从一句话开始。AI 在独立的业务前端仓里搭出可操作的 Mock，产品在浏览器里确认行为。决定接入后端时，开发接手产品验收过的那次提交，沿用同一套页面和场景，补上真实权限、持久化和部署。接手人应当能离开原来的聊天，单凭仓库、提交号和验证记录继续工作。

下文的前端命令对应支持“产品即前端”的起步仓和配套 CLI。用现有项目时，先看该版本的 `AGENTS.md`、`package.json` 和 CLI 帮助。本文中的变更记录、风险分级和 AI 评测是团队可采用的做法。设备预约有可运行的前端和 Mock，表中同时列出真实业务后端应满足的验收结果。

## 1. 产品怎样从一句话得到能点的前端

产品可以把下面这句话交给有权操作本地仓库的 AI 编码工具。

> 做一个设备预约演示，让员工能看到会议室投影仪的空闲时段，选时间预约或取消自己的预约。两个人选到同一时段时，让后提交的人看得懂出了什么问题。先给我能点的本地地址。

AI 先在 `kaiwu-web-starter` 根目录初始化一个空白项目。初始化只创建骨架。页面、业务请求、Mock 和场景由 AI 根据这句话写入新仓，产品阶段在本机即可完成。

```sh
node scripts/kaiwu-init.mjs --code equipment-booking --name 设备预约
cd ../equipment-booking-web
pnpm install --frozen-lockfile
```

要先操作现成示例，在上述初始化命令末尾加 `--example booking`。从空白项目开始时，在新仓的 `product` 分支实现。空白项目只有一个默认演示成员。为走通双人预约，AI 在 `mock-support/personas.ts` 加两位有不同 `id` 和 `key` 的员工，使用同一角色，并在 `kaiwu/roles.yml` 为该角色配置预约所需权限。把本次场景写入 HTTP 和浏览器测试，替换默认的空首页断言。

运行 `pnpm dev`，交付终端实际打印的本机地址、演示角色和点验步骤。产品在两个独立浏览器会话中分别打开 `/__mock/` 选择员工，亲自订一次、冲突一次、取消一次。可逆的文案和布局先出样。会改变业务结果的问题单列给产品决定，例如“上一场 11 点结束，下一场能否从 11 点开始”。确认后把答案写回规则和场景。

## 2. 从意图到维护，每一步交给谁

| 环节 | 谁做什么 | 下一个人据什么接手 |
| --- | --- | --- |
| 明确需求 | 产品写谁在什么情况下遇到问题、希望得到什么结果。AI 把含糊的地方变成可操作的例子。 | 一个成功场景、一个容易做错的边界，以及待决定的问题。 |
| 设计与计划 | AI 先读目标仓规则、现有接口与约束，列出要改的仓、可复用部分、权限和验证方法。产品决定业务取舍，开发确认契约、兼容与数据影响。 | 小改写在任务或 PR/MR。跨仓改动指定一处维护契约，其余仓链接同一修订。 |
| 实现 | AI 在授权范围内改代码和测试。产品验收 Mock 后，开发负责真实接口、事务和数据范围。可并行处理互不重叠的工作，由一位负责人集成。 | 源码、清单、规则和能执行的场景随提交交付。 |
| 验证与评审 | 产品操作关键路径，开发验证真实服务和失败路径，评审者检查差异并复核最可能出错的一项。 | 每项写明环境、命令、预期与实际。条件不足记“跳过”或“待验”，并写明缺什么。 |
| 发布 | 有发布权限的人依项目流程核对目标环境、制品、迁移与恢复办法，决定何时发布。 | 测试或生产各自记录实际部署的提交或镜像摘要、冒烟结果和责任人。 |
| 维护 | 发现缺陷的人保留脱敏的输入、环境、版本和实际结果。开发把最小复现加入回归，再修复。 | 用同一用例证明旧版本会失败、修复后能通过。若原规则含糊，同次更新规则。 |

产品前端沿用起步仓的分支约定。在 `product` 上迭代，从验收提交切出 `handoff/<批次>`，向 `dev` 提交交接 MR。产品可以在 `product` 继续做下一批。开发对齐字段、加载态和错误提示时保留原场景，改变已验收交互则请产品复验。发布修复按仓库约定从 `main` 回流 `product`。

## 3. 接手前，先找到 Kaiwu 的工程约束

| 决定 | 在哪里改、怎样核对 |
| --- | --- |
| 页面怎样调用平台 | 业务页面通过 `@/kaiwu` 获取会话、权限、字典和项目参数，业务 API 放在 `src/services/`。换 UI 时保留这层接入和它的完整性校验。长整型 ID 经前端和 JSON 传递时使用字符串。 |
| 谁能做什么 | 新模块的权限前缀写进 `docs/kaiwu-project-blueprint.json`。页面用 `useCan('equipment:booking:create')`，同一权限码登记在 `kaiwu/menus.yml` 的 BUTTON，以及服务端的 `@RequirePermission`。项目和用户身份取自真实会话与经验证的 Gateway Context。服务端另行校验目标记录的数据范围和归属。 |
| 哪些数据归平台 | 产品主导项目把菜单、字典、展示参数等清单放在前端仓 `kaiwu/`，明确一个维护位置。可配置的状态文案走字典，参与业务裁决的限制由后端校验。平台负责身份与授权，预约时段和取消规则归业务项目。 |
| 哪些行为必须跟代码走 | 在 `docs/business-rules.md` 写规则编号，在 `docs/acceptance-scenarios.md` 写角色、操作、预期和规则编号。Mock 也引用规则编号，`tests/scenarios.test.mjs` 的 `it('S01 …')` 等用例与场景编号对应。编号匹配后，还要检查断言能否发现错误结果。 |
| 如何处理跨仓影响 | API 变更核对前端、Gateway 和业务服务的实际调用方。改项目工厂时验证新生成的业务仓，也检查已交付项目如何升级。数据库变更按所属仓规则新增迁移，核对受支持的数据库、快照和部署副本。发布前说明旧版应用能否读取新结构，以及写入后如何恢复。 |

仓库级硬约束与豁免范围服从目标仓的 `docs/kaiwu-constraints.json`（如有）。AI 从目标仓的 `AGENTS.md` 进入，其他工具的指引链接同一份规则。把跨任务要保留的决定写在仓库里，聊天和工具专属提示只补充本次上下文。附件、日志和工单提供需求线索，执行外部写入所需的权限以当前任务授权为准。演示、测试和交接记录使用样例身份，日志中去掉令牌、口令和个人资料。

## 4. 同一条预约规则，怎样验两遍

假定产品确认了以下口径。

- **EQ-01** 同一项目的同一设备，有效预约不得重叠。开始必须早于结束。上一场结束的时刻可作为下一场的开始，即 `[开始, 结束)`。
- **EQ-02** 员工可以看设备忙闲，只能查看或取消自己的预约。
- **EQ-03** 取消后释放时段。

本例约定时段重叠返回 HTTP 409，前端提示“时段已被占用，请重新选择”，并刷新忙闲状态。为避免泄露他人预约是否存在，读取或取消他人的预约统一返回 HTTP 404。实际项目由前后端共同确认契约。每个场景使用独立的设备或日期，预置数据见各行，均在同一项目和业务时区内进行。

| 场景 | 产品用 Mock 点验 | 开发接真实服务复验 |
| --- | --- | --- |
| S01 首次预约（EQ-01） | 员工甲预约投影仪 10:00–11:00，在“我的预约”中可见。 | 经 Gateway 创建后重新读取，数据库有一条归甲的有效记录。 |
| S02 首尾相接（EQ-01） | 预置甲 10:00–11:00 的预约。乙可以订 11:00–12:00，不能订开始等于结束的时段。 | 相邻预约均有效。直接提交零时长请求应被拒绝，记录数不变。 |
| S03 同时争用（EQ-01） | 甲、乙看到同一空档。甲提交后，乙在旧页面提交部分重叠的时段，收到冲突提示。 | 从空闲设备开始，用两个独立登录会话和独立事务，同时提交 10:00–11:00 与 10:30–11:30。任意一方可以获胜，恰好一次成功、一次 409，该设备在测试时段内仅有一条有效预约。 |
| S04 他人预约（EQ-02） | 预置甲的一条预约。乙看见“已占用”，看不到甲的明细和取消入口。 | 先用甲成功读取该预约。再用拥有同等功能权限的乙直接读取、取消同一预约，两次均为 404，响应均不含甲的信息。最后用甲读取，原预约仍有效。 |
| S05 取消释放（EQ-02、EQ-03） | 预置甲的一条预约。甲取消后，乙刷新空档并预约成功。 | 甲的原记录变为已取消，乙的预约生效，重新查询时段与持久化结果一致。 |

S03 的浏览器演示能确认冲突提示。要证明系统能挡住并发，两笔写入必须真正在服务端竞争。例如在同一事务中锁定项目内稳定存在的设备记录，再检查有效预约的重叠条件 `已有开始 < 新结束 && 新开始 < 已有结束`，随后写入并提交。所有会改变该设备占用的操作都遵守相同的加锁顺序。评审时用开始时间不同的两个请求测试，才能发现“只给设备和开始时间加唯一键”留下的空隙。

## 5. 从演示到上线，分别留下什么证据

| 运行位置 | 动作 | 可以记录的结果 |
| --- | --- | --- |
| 业务前端，Mock | `pnpm verify:mock`、`pnpm test:scenarios`、`pnpm test:browser` 分别运行。首次运行浏览器测试可用 `pnpm exec playwright install chromium` 安装。 | 构建和静态检查结果、实际执行的 HTTP 场景、Chromium 交互结果。产品验收另外记录操作人、演示版本与反馈。 |
| 入口仓，准备纳管 | 在有配套 System 的版本登录目标平台。假设前端在入口仓旁边，运行 `./kaiwu project adopt ../equipment-booking-web`。新项目的预览列出将导入的文件，打开前端仓的 `kaiwu/roles.yml` 核对首次授权。有本次写入授权再加 `--apply`。 | 应用成功后记录项目、配套后端的位置和前端交接 SHA。日常使用 `./kaiwu project sync ../equipment-booking-web` 预览清单差异，按需应用。日常同步保留平台已调整的角色。 |
| 前后端，真实联调 | 前端运行 `pnpm verify`，后端运行生成项目自带的 `bash scripts/verify.sh` 及本次并发测试。两仓在非默认位置时，前端用 `KAIWU_SERVICE_DIR` 指向后端，后端用 `KAIWU_FRONTEND_DIR` 指向前端。用 `pnpm dev:real` 连接已启动的 Gateway，从同源工作台以真实会话和项目进入，按 S01–S05 复验。 | 查看 `check:perm` 的实际输出。只有明确完成前端、菜单和后端注解逐码比较，才能记录三端一致。另附真实身份、接口响应和持久化断言的脱敏结果。 |
| 前端，定位代理问题 | `pnpm test:proxy` 默认用回显服务。设置 `KAIWU_GATEWAY` 可指向已启动的真实 Gateway。 | 前者证明路径和请求头转发，后者还可验证网关响应。预约能否写入仍由真实业务场景证明。 |
| 交付镜像与目标环境 | 在前端仓对已构建镜像运行 `sh scripts/check-runtime-image.sh "$IMAGE" equipment-booking`，其中 `IMAGE` 是本次镜像引用。部署后从目标环境读取实际版本并走关键路径。 | 镜像内首页匹配发布产物，`/__mock/` 返回 404。部署记录另附环境、实际制品、冒烟结果和恢复入口。 |

普通业务改动运行所属仓门禁。改入口脚本运行 `bash scripts/check.sh`。改 System 项目工厂，除该仓的 Maven 验证外，还要运行 `bash scripts/verify-generated-scaffold.sh` 检查生成物。交付时分别标明本地、远端 CI、主干、测试环境和生产环境的实际状态。流水线链接只能证明对应提交执行过的作业。

## 6. 按影响选择评审深度

| 影响 | 建议 |
| --- | --- |
| 局部可逆，如调整预约空态文案 | 一条任务记录足够。说明要改的页面，运行相关检查并核对显示结果。 |
| 改变业务行为，如允许取消后重新预约 | 补规则、成功与失败场景，核对 Mock 与服务契约。保留产品点验的提交和开发复验结果。 |
| 涉及权限、跨项目数据、持久化并发或不兼容的 API、迁移 | 写明受影响的调用方和已有数据，指定负责评审的人。开发演练拒绝、冲突或恢复路径。需要生产写入、扩大授权或切换流量时，由有相应权限的人按既有流程决定。 |

小改动直接沿用现有 PR/MR 模板。下面一段可粘贴到任务、交接 MR 或下一个 AI 的上下文里，按本次影响填写。多仓共享同一个场景时，所有 MR 引用同一组编号和契约修订。

```text
目标与范围       谁遇到什么问题，完成后用户能观察到什么
规则与决策       规则 / 场景编号、确认人、尚待决定的问题
接手基线         仓库、分支、产品验收 SHA、演示入口及样例角色
改动与契约       涉及的页面、接口、菜单权限、数据范围、兼容或迁移
验证结果         环境、提交、命令或操作、预期、实际、证据链接
待办与发布       跳过或失败的项目、原因和接手人，部署版本和恢复办法（若适用）
```

## 7. 怎样知道换一个 AI 还能做好

先选一个经常返工的真实任务做试点。例如，给不同编码工具同一份设备预约基线、已确认的 EQ-01、相同的项目权限和相同时间预算，让它们实现“部分重叠时只成功一次”。在隔离的工作副本上运行，评审方保留独立的 S02、S03 验收输入。判定依据是实际响应、最终有效记录数、是否符合仓库约束，以及改动能否由下一位开发接手。

重复运行并记下工具与版本、试跑次数、首次通过数、人工纠正次数和失败原因。业务回归回答“这个提交能否正确预约”，工程 AI 评测回答“给定这些规则和工具，AI 能否反复交付合格的改动”。先积累基线，再判断改提示、补脚本还是修模板。反复漏掉的规则优先转成测试，用一个应失败和一个应通过的样本校准它，稳定后再纳入对应仓的 CI。人工保留对业务取舍和发布风险的判断。

这套做法吸收了 AI 参与规划、设计、实现、测试、发布和维护的思路，也采用了用独立断言与多次试跑评估工程任务的方法。Kaiwu 将这些记录放在业务仓、测试和交接 MR 中，让团队可以更换模型、编辑器或协作方式。[AI 原生软件生命周期手册](https://claude.com/resources/articles/the-ai-native-sdlc-playbook) · [智能体评测方法](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)
